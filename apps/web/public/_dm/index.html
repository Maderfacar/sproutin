01 — 為什麼是這樣做

不是把紙本搬上網，
是把重複的動作拿掉。

園所現在的困擾多半不是「沒有系統」，而是資訊散在 LINE 群組、紙本聯絡簿、電話與 Excel 之間， 同一件事要講三次、改三次。Sproutin 的三個設計前提就是為了處理這件事。

前提一

家長端的門檻必須是零

再好的系統，只要要求家長下載 App、註冊帳號、記密碼，就會有一半的家庭停在那一步 —— 然後園所又得回去用 LINE 群組通知。所以入口直接放在 LINE 裡。

  • 官方帳號選單點一下就進來
  • 身分靠 LINE 登入自動帶入
  • 重要通知直接推到 LINE 對話

前提二

同一份資料只維護一次

家長線上請假並被核准後，出缺勤、娃娃車名單、老師的待辦、家長端的狀態卡會自己跟著變 —— 老師不需要再手動去改第二個地方。

  • 學生資料是所有紀錄的唯一來源
  • 請假核准自動連動當日出缺勤
  • 轉班、休學一次改動全園生效

前提三

一次只做一種身分

園長兼導師、老師的小孩也在園裡，是幼兒園的常態。 與其在同一頁貼「以老師身分／以家長身分」的標籤讓人自己讀，不如整個介面換掉。

  • 頁籤、首頁、問的問題全部不同
  • 切成家長，後台入口整組消失
  • 權限判斷一律在後端，不靠畫面藏

03 — 園所的一天

同一件事，
只會被輸入一次。

下面是一個真實的早上：家長請假 → 老師收到 → 核准 → 出缺勤自動連動 → 家長手機收到通知。 中間沒有任何人需要「再去別的地方改一次」。

07:20

家長在 LINE 裡送出請假

點開園所官方帳號 →「請假」→ 選日期、選假別、寫原因 → 送出。全程在 LINE 內完成，沒有下載也沒有登入。

家長　立即在紀錄裡看到「待審核」，不必打電話確認學校有沒有收到。
07:34

導師首頁多了一件事

「請假審核 · 1 件等你決定」。點進去看到孩子名字、日期與原因，兩顆按鈕：准假／不准。不准一定要寫一句原因。

班導師　不需要在群組裡翻訊息找是誰請假、哪幾天。
07:35

核准的同時，四件事自己發生

當日出缺勤標為請假、娃娃車今日名單移除、家長端狀態卡改成「今天請假」、通知進入推播佇列。老師只按了一顆按鈕。

系統　連動走事件而非人工；每一步都寫入稽核紀錄。
07:35

家長的 LINE 響一聲

「范小星 8/21 的請假已核准」。點開通知直接回到 App 的對應頁面。

家長　不必再問一次「老師有看到嗎」。
08:30

老師點名：一下解決九成

打開就是今天這一班，一顆「剩下 21 人全部標到校」，之後只處理例外。最上面一直有進度與「已存檔」。

班導師　請假的孩子已經被系統排除，不必為他們花任何時間。
09:40

園長打開手機，看到的是全園

今天到校幾位、幾位請假、哪一班還沒點完名、有幾件請假等人決定。需要出手的地方自己浮上來。

園長 / 行政　不必逐班詢問，也不必等老師回報。
16:00

聯絡簿一次寫完一整班

「直欄模式」：一次只處理一件事（午餐／午睡／心情…）、全班一起，預設全班正常、只點例外。寫好按送出，家長才看得到。

班導師　逐生逐欄約需 175 次點擊，直欄模式約 25 次。

04 — 接著看

每一種身分，實際會看到什麼

02 · 家長

打開就是答案，不是功能表

今天的狀態、聯絡簿與親師對話、請假、娃娃車、公告與通知。逐頁模擬，含每一塊為什麼這樣排。

看家長端的每一頁

03 · 老師

一份會變短的待辦

點名、聯絡簿直欄模式、請假審核、班級名單。以及老師「刻意看不到」的東西。

看老師端的每一頁

04 · 園長 / 行政

手機看全園，電腦做管理

全園總覽、桌面後台、LINE 群發（兩段式送出）、園所外觀與圖文選單、人員綁定、權限、稽核紀錄。

看園務端的每一頁

05 · 平台

功能總表、權限、資安與藍圖

哪些已經上線、哪些規劃中；誰能做什麼的完整對照；資料如何隔離與留痕；導入需要準備什麼。

看完整規格

「介面需要標籤解釋自己，就是版面已經失敗了。」 —— 這套產品的設計原則之一。三種身分因此拆成三套殼，而不是同一頁貼身分標籤。
